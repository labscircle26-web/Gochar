4. Storage and Processing Architecture

Use existing infrastructure.

- Store original PDFs in a private Cloudflare R2 bucket.
- Store metadata and processing information in Supabase.
- Never expose public R2 object URLs.
- Use authenticated upload/download operations.
- Extract PDF text on the server.
- Preserve page numbers and chapter headings.
- Divide extracted text into meaningful searchable chunks.
- Store chunk text, book ID, page number, chapter and relevant metadata in Supabase.
- Create searchable indexes for efficient retrieval.
- Keep original PDFs available for viewing and reference.

Support:

- Normal text-based PDFs.
- Scanned PDFs where possible, using OCR as a separate processing step.
- Multiple languages where extraction support exists.
- Large PDF files through background processing.

Do not load entire PDFs into browser memory.

5. PDF Processing Status

8. Prediction Generation Logic

IMPORTANT: The Prediction Maker must use a deterministic calculation and rule-matching system.

Do not require a paid AI API.

The system should:

1. Receive the selected house and user's birth-chart data.
2. Retrieve verified astronomical and astrological calculations from the existing engine.
3. Identify applicable rules.
4. Retrieve supporting interpretations from the PDF knowledge base.
5. Evaluate supporting and conflicting indications.
6. Organize findings into structured prediction sections.
7. Generate readable text using interpretation templates.
8. Include source references wherever available.

The system must distinguish:

- Natal promise.
- Current Dasha influence.
- Current transit influence.
- Short-term changes.
- Long-term tendencies.

Do not treat a single planetary placement as sufficient to make a prediction.

Do not present contradictory indications as certain outcomes.

- Do not change the existing Lagna or birth-chart calculation logic.
- Keep natal birth data separate from the changing Gochar timestamp.
- Distinguish source-backed classical rules from newly created interpretations.
